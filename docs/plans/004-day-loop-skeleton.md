## 2단계에서 이 계획의 자리

2단계 전체를 한 계획에 넣지 않는다. 이 계획은 **뼈대**다: 고정된 의뢰 3건을 순서대로 듣고, 한 번씩 결투하고, 돈으로 정산받고, 가게를 닫는 데까지가 끊기지 않고 이어진다. 선택지(거절, 협상, 업그레이드)는 하나도 없다.

뼈대를 먼저 만드는 이유: 2단계에서 가장 먼저 알아야 하는 것은 "결투 세 판을 화면 사이에 끼워 연달아 했을 때 하루로 느껴지는가", "충족도가 돈이 되면 정확히 수행하고 싶어지는가"이고, 이것은 루프 전체가 이어져야만 확인된다. 거절·협상·업그레이드는 그 답을 본 뒤에 얹는 것이 싸다.

이 계획이 끝나면 9장의 완료 기준 "하루 3의뢰를 끝까지 플레이 가능"은 글자 그대로는 채워진다. 2단계를 거기서 끝낼지, 아래 남는 것을 2단계 안에서 더 만들지는 사용자가 플레이 뒤에 정한다(작업 5의 보고서 4번).

3. **평판과의 관계** — CLAUDE.md 6장의 평판(가게 별점), `Commission.reputation_effect`와 같은 점수인지 별개의 점수인지.

## 규칙 — 정산과 장부

수치는 전부 임시이고 `data/economy_rules.tres`에 있다. 계산은 정수 연산으로 하고 반올림은 0.5를 올린다. a x b / d의 반올림은 `(a x b x 2 + d) / (2 x d)`의 정수 나눗셈으로 한다(부동소수를 지나지 않는다).

### 결투 한 건의 정산

충족도는 지금 그대로 `Commission.evaluate(record)`다(0~100).

| 항목 | 계산 | 임시 수치 |
|---|---|---|
| 기본 보수 | `base_reward` x 충족도 / 100 | — |
| 팁 | 충족도가 `tip_floor` 이하면 0. 넘으면 `tip_max` x (충족도 − `tip_floor`) / (100 − `tip_floor`) | `tip_floor` 70 |
| 부상 | 결투가 내가 유효타를 맞아 끝났다(`record.end_reason == PLAYER_DEFEATED`). 자세만 깎인 것은 부상이 아니다 | — |
| 치료비 | 부상이면 `medical_fee`. 정산 화면에 알리고 폐점 때 낸다 | 20 |

보수 표 (T29가 이 숫자를 그대로 검사한다):

| 충족도 | 의뢰 (기본 / 팁 최대) | 기본 보수 | 팁 | 합 |
|---|---|---|---|---|
| 100 | 첫 피 (30 / 15) | 30 | 15 | 45 |
| 40 (머리) | 첫 피 | 12 | 0 | 12 |
| 0 | 첫 피 | 0 | 0 | 0 |
| 100 | 깃털 (45 / 25) | 45 | 25 | 70 |
| 90 (스침 1회) | 깃털 | 41 | 17 | 58 |
| 80 (스침 2회) | 깃털 | 36 | 8 | 44 |
| 70 (스침 3회) | 깃털 | 32 | 0 | 32 |
| 100 | 지기 (40 / 30) | 40 | 30 | 70 |
| 85 | 지기 | 34 | 15 | 49 |
| 71 | 지기 | 28 | 1 | 29 |

이 공식이 만드는 것: 기본 보수는 "얼마나 해냈는가"에 비례하고, 팁은 거의 흠 없이 해냈을 때만 붙는다. 깃털에서 몸을 한 번 스치면 팁의 3분의 1이 날아간다. 승패는 돈에 들어가지 않는다(원칙 2).

### 하루의 장부

- 수입은 정산 때마다 소지금에 더한다. 지출은 폐점에 들어설 때 한 번 뺀다.
- 지출 = 임대료(`rent`, 임시 60) + 치료비 x 부상 횟수.
- 시작 소지금은 `starting_money`(임시 0).
- 예: 첫 피 100 / 깃털 90 / 지기 85(패배) → 수입 45 + 58 + 49 = 152, 지출 60 + 20 = 80, 손익 +72. 완벽한 하루는 수입 185, 손익 +105다. 첫 피만 해내고 나머지를 망치면 적자다.

### 하루의 단계

`COUNTER`(의뢰인의 사연) → `DUEL` → `SETTLEMENT` → 다음 의뢰가 있으면 `COUNTER`, 없으면 `CLOSING` → 다음 날이면 `COUNTER`.

- 단계에 맞지 않는 요청(카운터에서 결투 끝내기 등)은 아무것도 바꾸지 않고 거짓을 돌려준다. 오류를 찍지 않는다(테스트 래퍼가 오류 줄을 실패로 본다).
- 하루의 의뢰가 0건이면 곧바로 `CLOSING`이다.
- 하루 중의 결투는 한 번뿐이다. R(다시 하기)과 Esc는 듣지 않는다. 결투가 끝나고 결과 패널이 뜬 뒤 Space 또는 Enter로 정산에 간다. 마우스 클릭으로는 넘어가지 않는다(결투 중의 클릭이 이어져 결과를 넘겨 버리지 않게).

### 작업 4. 하루 통째 스모크와 화면 확인

    - 결투: 먼저 R과 Esc 입력을 보내 코어와 현재 씬이 그대로인지 본다(하루 모드의 `retry`·`back` 무시). 그다음 끝날 때까지 `advance`를 불러 시간을 빨리 흘리고(입력 없이 진다) `ui_accept` 입력을 보낸다
    - 폐점: 결과가 3건인지, 소지금이 "시작 소지금 + 결과들의 합 − 임대료 − 치료비 x (결과에서 센 부상 횟수)"인지 본다. 부상 횟수를 3으로 가정하지 않는다(스모크의 결투는 난수가 고정되지 않는다). 그다음 `Proceed`를 눌러 2일차 카운터가 현재 씬이 되는 것까지 본다
    - 성공하면 `DAY SMOKE OK`와 장부 한 줄을, 자체 프레임 상한(3000. `--quit-after` 6000보다 작게)을 넘거나 확인이 틀리면 `DAY SMOKE FAIL`과 이유를 찍는다. 찍은 뒤 러너처럼 실제 시간 0.3초(`Time.get_ticks_msec()`로 잰다)를 기다렸다가 종료 코드 0 또는 1로 끝낸다(비프음 재생 객체의 누수 줄을 피한다)
  - `tests/run_smoke.ps1` (ASCII만) — `cmd /c "<godot> --headless --path <프로젝트> res://tests/day_smoke.tscn --quit-after 6000 2>&1"`로 돌려 출력을 그대로 보여 주고, 종료 코드 0 · `DAY SMOKE OK` 줄 · 오류 줄 0을 모두 요구해 마지막 줄에 `RESULT: OK` 또는 `RESULT: FAIL (이유)`를 찍는다
  - 화면 확인: 운전 노드는 헤드리스가 아니고 명령줄 사용자 인자로 폴더(`-- --shots=<폴더>`)를 받았을 때, 화면마다 한 프레임 이상 그려진 뒤 뷰포트를 PNG로 저장하고 넘어간다. 저장할 화면: 처음 화면, 카운터 셋(의뢰마다), 하루 모드의 결과 패널, 정산, 폐점. 폴더는 저장소 밖(임시 폴더)이다. 메인 에이전트는 그 PNG를 열어 본다: 글자가 잘리거나 겹치지 않는가, 지기 의뢰의 긴 대사(두 문단)가 말풍선 안에 들어가는가. 정산·폐점·하루 모드 결과 패널은 씬을 직접 띄워서는 볼 수 없다(`day`가 없으면 처음 화면으로 돌아간다)
- 완료 확인: `powershell -ExecutionPolicy Bypass -File tests/run_smoke.ps1`의 마지막 줄이 `RESULT: OK`. 테스트는 여전히 `ALL PASS 34/34`. PNG에서 본 것을 보고서 2번에 적는다.
- 스모크가 돌지 않을 때의 순서
  1. 먼저 축소한다: 입력 주입과 버튼 누르기를 빼고, 운전 노드가 `GameSession`의 "하루 시작"과 "지금 단계의 씬으로 가기", `DayState`의 전환을 직접 불러(결투 끝은 그 씬의 코어 기록을 넘긴다) 다섯 씬이 차례로 현재 씬이 되는지와 폐점의 장부만 본다. 이것만으로 위 접착 코드의 대부분이 덮인다. 축소했으면 빠진 확인(버튼 → 전환 연결, 하루 모드의 Esc·R 무시, Space로 넘기기)을 보고서 2번의 "확인 못 한 것"에 적는다
  2. 축소한 것도 돌지 않을 때만 생략한다. 그때는 "확인 못 한 것" 맨 위에 "실제 씬 전환과 `GameSession` 경로 전부"를 적는다
  3. PNG 저장만 안 되면 스모크는 그대로 두고 "화면 확인 못 함"을 적는다

## 위험

- **세 판이 전부 같은 상대다.** 둘째 판부터는 버릇을 이미 안다. "하루로 느껴지는가"의 판단이 "같은 상대라 지겹다"에 묻힐 수 있다. 대비: 체크리스트 I가 따로 묻는다. 상대를 더하는 것은 9장의 4단계·6단계와 겹치므로 이 계획에서는 하지 않고, 필요하면 사용자가 정한다.
- **한 번뿐인 결투가 억울할 수 있다.** 특히 지기는 요령을 모르면 점수가 낮다. 대비: 연습이 남아 있다. 체크리스트 I.
- **화면이 많아 결투 사이가 늘어질 수 있고, 채점표가 의뢰인의 반응보다 먼저 온다**(결과 패널 → 정산 → 다음 의뢰인). 대비: 체크리스트 I, 결정 38의 되돌리기.
- **돈을 쓸 곳이 없다.** 손익이 숫자로만 남아서 "돈이 신경 쓰이는가"의 답이 공식 때문인지 쓸 곳이 없어서인지 섞인다. 대비: 체크리스트 I와 보고서 4번이 둘을 가려 묻는다.
- **Space를 누르던 손이 사연을 넘겨 버릴 수 있다.** 카운터의 "맡는다"가 처음부터 포커스를 가진다. 대사의 버릇 힌트는 관찰의 통로다(원칙 4). 대비: 이 계획에서는 고치지 않고 체크리스트 I로 본다.
- **보수 수치는 손으로 정했다.** 대비: 전부 `.tres`, 체크리스트 I.
- **`ui_accept`가 헤드리스 테스트에서 없을 수 있다.** 기본 액션은 프로젝트 액션과 같은 경로로 `InputMap`에 올라오므로 아마 있다. 대비: 작업 2의 T0 보강과 `confirm` 액션으로의 대체.
- **키를 누른 채 화면이 바뀌어 다음 화면까지 넘어갈 수 있다.** 포커스된 버튼은 반복 입력을 무시하고 누름을 자기가 받았을 때만 발동하므로 엔진이 대부분 막는다. 결투 씬은 반복 입력을 받지 않는다. 실제로 그런지는 사용자만 확인할 수 있다(체크리스트 I).
- **씬이 켜질 때의 `_ready`에서 트리를 건드리면 오류가 난다.** 대비: 공통 규칙의 `call_deferred`, 작업 3의 씬 직접 실행 셋.
- **스모크의 운전 노드가 타이밍 때문에 서지 않을 수 있다.** 대비: 알려진 함정을 작업 4에 적었고, 생략 전에 축소 단계가 있다. 생략되면 사용자의 첫 클릭이 `GameSession` 경로의 첫 확인이 된다.
- **손으로 쓴 `.tres`의 타입 배열이 로드되지 않을 수 있다**(`DayData.commissions`). 대비: T28. 막히면 일회용 스크립트에서 `ResourceSaver.save()`로 만든다(계획 001의 선례).
- **결투 씬의 분기가 연습 경로를 깨뜨릴 수 있다.** 대비: T14·T22·T24를 고치지 않고 통과시킨다.
- **planner와 검토자는 아무것도 실행하지 못했다.** 보수 표는 손 계산이고(두 검토자가 다시 계산해 맞았다), 엔진 동작에 관한 서술은 실행 결과가 아니다. 대비: T29가 표를 그대로 검사하고, 어긋나면 멈춘다.

## 검토 대응 기록

### 1회차 (v1 → v2, 둘 다 REVISE)

**차단 사항**

- **D1 (승리 보상을 임시값으로 구현하면서 "사용자 결정 필요"를 "없음"으로 적음) → 수용, 제안 (B)로.** 명예 구현을 계획에서 뺐다. 빠진 것: v1의 결정 38·39, 조건 타입의 여섯 번째 메서드와 `commission.gd`의 덧붙임, `EconomyRules.win_honor`, 규칙 표의 "승리"·"명예" 행, T28의 해당 줄, T30·T31의 명예 기대값, 카운터·정산·폐점의 명예 표시, 체크리스트 I의 명예 묶음, 관련 위험 둘. 사용자 지시("만들 예정")와 세 물음은 새 절 "승리 보상"에 남기고 보고서 4번으로 보낸다(결정 41). 이제 "없음"은 사실이다.
  - (A)가 아니라 (B)를 고른 이유: 뼈대는 이 답에 기대지 않는데, (A)는 사용자가 스스로 "아직 안 정했다"고 했고 물음을 보고도 답하지 않은 것에 뼈대의 실행을 묶는다. 검토자가 든 "지금 물어야 싸다"의 근거는 (나)가 남은 계획의 순서를 바꾼다는 것인데, 그 순서는 이 계획의 보고 뒤에 정하므로 보고서 4번에서 묻는 것으로 제때다. 물음 자체는 메인 에이전트가 이미 사용자에게 보여 줬다.
  - 검토자의 지적대로 (가)는 지금의 규칙에서 "조건을 채우는 타격"과 같은 사건이고 1장의 중심과 엇갈리는 신호를 낸다는 점, (나)가 사용자 문장의 뜻에 가장 가깝다는 점을 "승리 보상" 절의 선택지 설명에 적었다.
- **T1 (실제 씬 전환을 확인하는 길이 쓰인 대로는 서지 않고, 서지 않으면 생략된다) → 수용, 제안 넷 전부.**
  1. 공통 규칙에 "`_ready` 안의 씬 전환과 뿌리에 붙이기는 `call_deferred`"를 넣었고, 작업 3의 "잘못 열린 화면"과 작업 4의 스모크 시작에 적용했다.
  2. 작업 3의 완료 확인에 카운터·정산·폐점 씬의 직접 실행 셋을 더했다.
  3. 작업 4에 운전 노드의 함정을 적었다: 현재 씬 null 건너뛰기, owned를 끈 `find_child`(공통 규칙에도), 종료 전 0.3초 실시간 대기, 자체 프레임 상한 3000, 부상 횟수를 결과에서 세기.
  4. 생략 앞에 축소 단계를 두었고, 생략은 축소한 것도 돌지 않을 때로 한정했다.
