# 인수인계 — 2026-11-20 16:30에 멈춘 지점

이 파일은 다른 컴퓨터의 새 세션이 읽고 이어 가기 위한 것이다. 사용자가 "계획 계속 진행해줘"라고 하면 이 파일의 "1. 바로 다음에 할 일"부터 시작한다. 이어 받은 세션은 일을 마칠 때마다 이 파일을 지금 상태로 고치거나, 더 필요 없으면 지운다.

- 브랜치: `stage2-day-loop-v2` (원격에 올라가 있다)
- 멈춘 까닭: 사용자가 16:30에 커밋하고 올리라고 예약했다. 오류로 멈춘 것이 아니다.
- 멈춘 때의 상태: 돌고 있는 하위 에이전트가 없었고, 중간에 끊긴 코드 수정도 없었다.

## 1. 바로 다음에 할 일

**계획 016(저장)의 "실행 전에 물을 것" 두 가지에 사용자 답을 받는 것**이다. 계획은 `docs/plans/016-save.md` v1이고 아직 검토 전이다.

메인이 2026-11-20 16:10쯤 두 물음을 사용자에게 글로 보여 줬고, 답을 받지 못한 채 멈췄다. 사용자에게 다시 물어야 한다. 물음과 선택지는 계획 파일의 "실행 전에 물을 것" 절에 있다.

1. 저장은 언제 되고, 하루 중에 그만두면 어떻게 되는가.
   - 가(권하는 안): 하루 단위로 저장하고, 그만두면 그날 아침으로 돌아간다.
   - 나: 하루 단위로 저장하고, "오늘은 그만"이 일찍 문 닫기(폐점)가 된다.
   - 다: 손님마다 저장하고, 끈 자리에서 이어진다(계획을 다시 써야 한다).
2. 저장이 있을 때 "새로 시작한다"가 어떻게 지우는가.
   - 가(권하는 안): 두 번 눌러야 지워진다.
   - 나: 바로 지운다.
   - 다: 새 가게의 첫날을 마칠 때 지운다.

답을 받은 뒤의 순서(CLAUDE.md 11장):

1. 답이 둘 다 "가"면 계획 본문이 이미 그 안으로 쓰여 있다. planner에게 "실행 전에 물을 것"을 답을 받았다고 고치게 한다(검토 전 수정이라 검토 횟수에 들지 않는다). 답이 다르면 planner가 같은 파일을 고친다.
2. design-reviewer와 tech-reviewer를 동시에 부른다(1회차). 물음 1의 사용자 답은 "지켜야 할 사용자 요구"로 전달한다.
3. 둘 다 APPROVE면 계획을 실행한다.

**016을 실행하기 전에 사용자에게 확인할 것**: 계획 015의 실행 확인을 먼저 할지. planner와 메인 모두 먼저 하기를 권했다(아래 3번). 사용자는 아직 답하지 않았다.

계획 016은 2단계의 마지막 작업이다. 실행하고 나면 2단계 완료 판정과 3단계로 넘어갈지를 사용자가 정한다(CLAUDE.md 9장).

## 4. 사용자가 보류했거나 아직 답하지 않은 결정

값은 전부 지금 그대로 두고 있다. 사용자가 다시 말하기 전에는 건드리지 않는다.

- 계획 012 보고서 4번: 승리의 값(+1), 별에 따른 하루 결투 수, 궂은일을 맡는 값, 별이 차는 속도, 토마소를 못 해냈을 때의 합. 사용자가 "보류"라고 했다.
- 계획 013 보고서 4번: 기본 보수 덧붙임의 크기(±20%), 낮은 별의 깎임.
- 계획 014 보고서 4번: 100점 조건이 팁에도 걸리는 것, +30%와 의뢰인의 값.
- 계획 015 보고서 4번: 거절의 대가를 누르기 전에 보이는 것, 확률표의 값, 돌려보내면 감점이 사라지는 것. 디자인 검토자가 올린 의견 셋(같은 성향 문구의 두 손님, 잘하는 플레이에서는 늘 누르는 것이 정답, 거절 대답이 한 가지)도 여기에 있다.
- playtester가 올린 것(`docs/reports/014-counter-haggle.md` 끝): 정산과 폐점의 평판 줄이 패널 밖에 놓이는 것, 폐점의 소지금 표기(`소지금 -18 → -78`)와 `치료비 -0`, 테스트 T53의 이름에 남은 옛 평판 값.

## 5. 이 컴퓨터의 메모리에만 있던 작업 규칙

다른 컴퓨터의 세션에는 이 규칙들이 없다. 사용자가 2026-11-20에 정한 것이다.

- **메인 에이전트는 테스트와 게임을 직접 실행하지 않는다.** `tests/run_tests.ps1`, `tests/run_smoke.ps1`, 헤드리스 Godot, `play.ps1` 전부다. 모델과 상관없다.
- **실행 확인은 사용자가 요청할 때만 `playtester` 에이전트에게 맡긴다.** 스스로 띄우지 않는다. `playtester`는 Opus 5.5로만 돈다. 호출할 때 모델과 effort 인자는 생략해 에이전트 정의를 따른다(CLAUDE.md 11장). Opus 5.5로 돌 수 없으면 멈추고 까닭을 보고한다.
- 세션 모델이 Fable 5.2일 때는 어떤 방식으로도 테스트를 돌리지 않는다. Opus 5.5만 돌릴 수 있다.
- 그래서 계획의 완료 기준은 코드 읽기, Grep, 값 대조, 손 계산으로 잡고, 실행이 필요한 확인은 보고서의 "playtester에게 맡길 확인" 목록으로 적는다. 작업 보고(CLAUDE.md 10장)의 2번에는 돌리지 않은 확인을 "확인 못 한 것"으로 적는다.
- 스크립트를 실행 없이 고칠 때는 계획 012~015의 "공통 규칙"(기계적 확인 다섯 가지)을 따른다: 들여쓰기 Grep(탭만), 같은 함수 안의 이름 겹침, `:= .*\.get\(`와 `:= .*\[`의 타입 추론, 서식 문자열의 자리 수와 `%%`, `@warning_ignore("integer_division")`의 위치.
- 사용자가 "NNN 계획 보고서"라고 하면 `docs/reports/`의 그 번호 파일을 그대로 보여 준다(예: "004 계획 보고서"는 `docs/reports/004-day-loop-skeleton.md`).
- 이 프로젝트를 만든 컴퓨터(Windows)에는 쓸 수 있는 Python이 없었다(`python`은 스토어 연결 파일이다). 계산이 필요하면 셸이나 손 계산으로 했다. 다른 컴퓨터는 다를 수 있다.
- 계획 하나의 검토는 2회가 상한이다(CLAUDE.md 11장). 하위 에이전트가 큰 편집 도중 응답이 끊긴 적이 있어, planner에게 편집을 작게 나눠 하라고 부탁해 왔다.
